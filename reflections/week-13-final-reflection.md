## Part 3 — What You Actually Learned

**3a. Pick the concept from this semester that took the longest to actually understand — not just to implement, but to understand. Describe what you thought it was before you understood it, what changed, and how you would explain it now to a student who was exactly where you were at the start of the semester.**

> Your answer: The Communication Pattern between the UI and the API
The UI I could understand. I mean, you truly can just read it top to bottom to understand the jist of what is being put on screen. But when it comes to the network side and the amount of jumping around different levels of abstraction to get to the API call, that is where I would struggle. One of my misconceptions was that for the `MediaApiService interface`, I figured wherever it was being implmented would need to flesh out / define the functions that we were giving to it. However, only after manually tracing the calls one day from UI to API (through the viewModel, repository, RetrofitInstance, etc) did I understand that it was Retrofit that was implmenting the interface, which is designed to understand how to implement the functions we were giving it marked as `@POST`, `@PUT`, `@GET`, and `@DELETE`. So we didn't have to actually define the calls in retrofit; we defined the steps to making those calls in our repositories, then having retrofit do the actual calls / serialization.

**5b. A friend tells you they want to learn Android development. Based specifically on your experience this semester — not what you've read, what you lived — what is the one thing you would tell them to understand before they write a single line of code?**

> Your answer: Write your API first
Part of what made this project a bit easier to understand, was knowing what calls the API was equipped to handle / what it means to get specific responses. However, if you try to build an app under the assumption that the API will be made later, I feel you may dig yourself into a hole by assuming some judgements / tasks should be determined by the API, and not by your own logic. Flesh out the API first, document EXACTLY what it does / how it reacts to different scenerios, note what data it expects and what it will give, THEN write the code to utilize that functionality just as we did.
